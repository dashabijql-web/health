- 默认保留用户当前工作树改动，不回滚已有改动。

- 每完成一个治理项，必须有对应验证动作。

## 4. P0 清单：必须先止血（第一轮已完成）

### P0-01 Redis 健康数据缓冲防毒化（已完成）

位置：

- `HealthData/src/main/java/com/xzkj/health/service/RedisHealthBufferService.java`

问题：

- 当前实现先批量读取 Redis，再在 `try` 外做 JSON 反序列化。
- 只要队列中有一条坏 JSON，整个 flush 会在进入写库 `try` 之前失败。
- 失败后该坏数据不会被 trim，后续 flush 会持续读到同一条坏数据。
- 结果是后续健康数据全部被堵在 buffer 中，形成“毒化队列”。

要做什么：

- 将 JSON 反序列化也纳入异常边界。
- 单条坏记录不能卡死整批写库。
- 增加死信队列或坏数据隔离机制。
- 增加 buffer 长度、坏记录数量、重试次数日志。
- 双库场景下要同时覆盖 `health:buffer:old` 和 `health:buffer:new`。

验收标准：

- 向 Redis 插入 1 条坏 JSON，不影响后续正常数据写库。
- 坏数据被隔离或记录，不会永久堵住队列。
- flush 日志能区分：
  - 读队列成功
  - 反序列化失败
  - 写库失败
  - trim 成功

优先级说明：

- 这是“持续写入链路”的核心止血项。
- 不修这个，系统可能在无人察觉下长期积压数据。

问题：

- 当前只校验了：
  - 只允许 `SELECT/ WITH`
  - 禁止注释
  - 禁止多语句
  - 限定表名
- 没有真正的程序级结果集限制和复杂度限制。
- “尽量控制 100 行以内”只写在 prompt 里，不是硬规则。

要做什么：

- 禁止或改写危险模式：
  - `SELECT *`
  - 无时间过滤的大表明细查询

- 增加 AI 查询审计日志：

- 对“查全部历史明细”“列出全部记录”这类问题，系统能拒绝或自动收敛。
- 单次 AI 查询不能无限制返回明细大表。
- 出现慢查询时能追踪到具体 SQL 和来源问题。

### P0-04 ThreadLocal 数据源上下文与异步任务收口（已完成）

位置：

- `HealthData/src/main/java/com/xzkj/health/config/datasource/HealthDataSourceContext.java`
- `HealthData/src/main/java/com/xzkj/health/controller/HealthPortraitController.java`
- `HealthData/src/main/java/com/xzkj/health/service/SleepService.java`

问题：

- 项目通过 `ThreadLocal` 保存当前数据源。
- 但项目同时大量使用：
  - `@Async`
  - `CompletableFuture.supplyAsync`
- 一旦线程切换，`ThreadLocal` 上下文可能丢失。
- `HealthPortraitController` 和 `SleepService` 直接使用裸 `supplyAsync` 跑 mapper，风险最高。

要做什么：

- 禁止裸 `CompletableFuture.supplyAsync()` 直接跑数据库查询。
- 统一改为受控执行器。
- 封装“携带数据源上下文的异步执行工具”。
- 对并行查询链路增加切库一致性测试。

验收标准：

- 当请求指定某个数据源时，并行查询不会偷偷回落到默认源。
- `old/new` 两库切换后，并行接口结果一致且可验证。

  - 密钥无效
