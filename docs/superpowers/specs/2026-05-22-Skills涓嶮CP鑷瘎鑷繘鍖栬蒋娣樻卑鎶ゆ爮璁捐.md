# Skills 与 MCP 自评、自进化、软淘汰护栏设计

## 1. 背景

当前工作区已经有较强的 runner、audit、双库、自动回归和夜间 supervisor 护栏，但对 `skill`、`MCP`、提示模板和调用编排本身，仍缺少一套必须遵守的治理规则。结果是：

- 某个能力是否值得继续使用，容易凭感觉判断。
- 某个能力失稳后，容易反复被默认调用。
- “自我进化”容易退化成“自由改自己”，甚至绕过现有验证链路。
- 外部 / 内置能力与本地可写能力的边界不清，容易误判成“都能自动修”。

本设计的目标不是做一个复杂评分平台，而是在 `AGENTS.md` 中增加一段必须遵守的项目级护栏，让本工作区后续的 skills / MCP 自我评估、自我进化、自我淘汰行为有统一边界。

## 2. 目标与非目标

### 2.1 目标

- 为 `skill`、`MCP`、提示模板、调用编排定义统一治理范围。
- 明确什么叫“自我评估”、“自我进化”、“自我淘汰”。
- 把状态流转、证据要求、自动权限、人工接管点写成强制规则。
- 让规则能够接入现有 runner / supervisor / backlog，而不是停留在口号层。

### 2.2 非目标

- 不在第一版引入复杂分数模型或自动排名系统。
- 不允许自动改动外部 / 内置能力的实现。
- 不试图让 skills / MCP 脱离现有 `AGENTS.md`、双库、隐私、验证规则单独运行。

## 3. 方案比较

### 3.1 方案 A：纯原则护栏

只在 `AGENTS.md` 写若干原则，例如“要持续评估”“低价值能力应淘汰”。

优点：

- 写得快。
- 对现有流程侵入小。

缺点：

- 容易沦为口号。
- 缺少状态流转和执行口径。
- 后续很难接入 runner / supervisor。

### 3.2 方案 B：强制护栏 + 证据化流程

在 `AGENTS.md` 中写死治理对象、状态机、准入 / 降级 / 软淘汰 / 恢复条件、固定证据、自动权限和禁止项，并要求结果进入固定产物。

优点：

- 同时具备规则性和可执行性。
- 容易与现有 run 产物、summary、backlog 对接。
- 能减少“这次例外”的随意解释。

缺点：

- 文档会比纯原则版更长。
- 需要定义最小记录字段。

### 3.3 方案 C：自动治理优先

直接让 supervisor 或编排器自动给 skills / MCP 打分、切换、淘汰。

优点：

- 自动化程度高。

缺点：

- 当前阶段误伤风险高。
- 容易在根因不清时同时替换多个对象。
- 很容易反过来污染测试和结论。

### 3.4 推荐方案

采用方案 B：`强制护栏 + 证据化流程`。

## 4. 治理对象与适用范围

所有被当前工作区使用到的下列对象，均纳入治理：

- `skill`
- `MCP`
- `prompt-template`
- `orchestration`，即 runner / supervisor / 代理编排中的调用节点、路由条件、回退条件、熔断条件

治理对象分为两类：

### 4.1 本地可写对象

指当前工作区内可修改、可提交、可回退的对象，例如：

- 本地 skill 文档或本地规则模板
- 本地 supervisor / runner 调用编排
- 本地提示模板或本地路由逻辑

这类对象允许在满足条件时自动调参、降级、软淘汰和恢复为候选。

### 4.2 外部 / 内置对象

指已安装、内置、外部依赖或当前工作区无法安全改写的对象，例如：

- 全局已安装 skill
- 外部 MCP server
- 平台内置能力

这类对象允许被评估、被降级建议、被软淘汰建议、被移出默认编排，但不允许自动修改其实现。

## 5. 核心定义

### 5.1 自我评估

不是对象自己宣称“我有用”，而是必须基于本地证据判断：

- 是否真的完成目标
- 是否稳定
- 是否可验证
- 是否成本可接受
- 是否引入新风险
- 是否仍优于替代方案

### 5.2 自我进化

不是自由改自己，而是：

- 只能作用于本地可写对象
- 只能做小步、单变量、可回退的调整
- 每轮只允许一个主问题
- 改后必须走对应验证

### 5.3 自我淘汰

第一版默认采用 `软淘汰`：

- 对象不会被删除
- 但默认不再进入自动调用链
- 只能人工显式放行，或满足恢复条件后回到 `candidate`

## 6. 状态机

每个治理对象必须处于以下状态之一：

- `candidate`
- `active`
- `restricted`
- `soft-retired`
- `frozen`

### 6.1 candidate

新接入或刚被修改，只能小范围观察，不能直接成为默认自动链路首选。

### 6.2 active

默认可用，允许被自动选择。

### 6.3 restricted

已降级，只能在限定场景使用，或需要显式理由才能调用。

### 6.4 soft-retired

软淘汰，默认不再参与自动调用链，但保留人工恢复入口。

### 6.5 frozen

人工冻结，用于高风险事故、隐私或权限问题、破坏性行为嫌疑；不能自动恢复。

## 7. 状态流转条件

### 7.1 准入：candidate -> active

必须同时满足：

- 有明确用途，且相对现有能力有清晰增益。
- 有明确输入、输出、失败表现、适用边界。
- 至少经过一轮真实任务或回归链路验证。
- 没有引入新的 blocker / high 风险。
- 本地可写对象有回退路径；外部 / 内置对象有替代方案。

### 7.2 降级：active -> restricted

满足任一项即可：

- 连续出现误判、空转、重复劳动、错误路由。
- token、耗时、人工复核成本明显高于收益。
- 输出质量不稳定，同类任务需要频繁补救。
- 与 `AGENTS.md`、双库、runner、隐私或验证规则冲突。
- 上游环境变化后不再稳定，但暂时还不至于淘汰。

降级后的默认动作：

- 不再作为首选。
- 必须记录“为什么这次仍要用它”。
- 优先走更稳的替代链路。

### 7.3 软淘汰：restricted -> soft-retired 或 active -> soft-retired

满足任一项即可：

- 连续多轮评估低价值，且已有更稳替代方案。
- 多次导致回归、污染结论、误导修复方向。
- 长期无人维护，文档漂移严重，恢复成本高于重建成本。
- 外部 / 内置对象虽不可自动修改，但已被证据证明不适合作为默认依赖。
- 降级观察期后仍未恢复稳定。

软淘汰后的默认动作：

- 从默认自动链路移除。
- 不能在无人值守进化流程里自动再次启用。
- 只能人工显式放行，或满足恢复条件后先回到 `candidate`。

### 7.4 恢复：restricted / soft-retired -> candidate

必须同时满足：

- 触发问题已被修复或可被稳定规避。
- 有新的验证证据，而不是凭主观猜测。
- 至少完成一轮受控试运行。
- 恢复后先回到 `candidate`，观察通过后才能回到 `active`。

### 7.5 冻结：any -> frozen

满足任一项即可：

- 隐私数据、真实写库、认证态、权限边界出现风险。
- 存在越权、破坏性动作、错误环境写入风险。
- 影响 runner / audit / summary 基础可信度。

`frozen` 只能人工解除，不能自动恢复。

## 8. 证据规则

所有升降级、软淘汰、恢复决策必须基于本地证据，不能只凭主观印象。证据优先级：

1. 当前代码、当前配置、当前调用脚本
2. 当前 run 产物、summary、日志、截图、metrics
3. `AGENTS.md`、`HEALTH_AUTONOMOUS_EVOLUTION_RUNBOOK.md`
4. 外部文档、issue、案例

## 9. 每轮必须记录的最小字段

凡是参与本轮自动链路的治理对象，至少记录：

- `object_id`
- `object_type`
- `current_state`
- `task_scope`
- `expected_value`
- `actual_outcome`
- `verification`
- `risk_notes`
- `decision`
- `decision_reason`

## 10. 评估维度

第一版不引入复杂评分，只按以下六类维度做证据化判断：

- `有效性`
- `稳定性`
- `可验证性`
- `成本`
- `风险`
- `替代性`

## 11. 固定产物

第一版至少需要两类固定产物：

- `AGENTS.md`
  - 用于写死必须遵守的规则、状态机、禁区、人工接管点
- `tests/evolution-backlog.json`
  - 用于记录候选问题、降级建议、软淘汰对象、恢复候选

后续如有需要，可再增加单独的治理台账，例如 `tests/skills-mcp-governance.json`，但不是第一版前置条件。

## 12. 自动权限边界

### 12.1 允许自动做的事

仅限本地可写对象，且只能做低风险动作：

- 调整调用优先级
- 从 `active` 降到 `restricted`
- 从 `restricted` 降到 `soft-retired`
- 从 `soft-retired` 恢复到 `candidate`
- 调整提示词的小步措辞、顺序、边界说明
- 调整编排层的路由条件、回退条件、熔断条件
- 为对象补充本地文档、使用边界、失败案例记录
- 在 backlog 中登记 `待替代 / 待重建 / 待恢复`

### 12.2 绝对禁止自动做的事

不论对象类别，以下动作都必须人工明确批准：

- 新增会接触隐私数据、真实业务写入、认证态、生产环境的默认自动能力
- 删除 skill / MCP / 提示模板的实现文件
- 修改高层治理规则来绕过本护栏
- 让 `soft-retired` 或 `frozen` 对象直接回到 `active`
- 把外部 / 内置对象伪装成本地可控对象处理
- 关闭验证、伪造验证、跳过验证后仍宣称通过
- 为证明某对象有效而改测试口径、summary 口径或日志口径
- 在无明确证据时访问更高权限的工具、目录、数据库或网络
- 在无人值守模式下自动启用破坏性命令、回滚、删文件、改数据库数据
- 在根因未清楚前，同时替换多个高耦合对象

## 13. 外部 / 内置对象的允许动作

外部 / 内置对象只能：

- 被记录表现
- 被建议降级
- 被建议软淘汰
- 在编排层被减少使用或移出默认链路
- 被标记为“只可人工显式调用”

外部 / 内置对象不能：

- 被自动改源码
- 被自动改安装形态
- 被自动伪造能力说明
- 被自动恢复成默认首选

## 14. 人工接管点

出现以下任一情况，必须停止自动进化并转人工：

- 涉及隐私、认证、真实写库、双库路由、权限边界
- 连续两轮以上无法明确归因
- 同一对象短期内反复 `active -> restricted -> candidate -> restricted`
- 需要同时动多个高耦合对象才能继续
- 本地证据互相矛盾
- 影响 runner / supervisor / audit 基础可信度
- 出现“为了证明自己有效而改变裁判”的迹象

## 15. 与现有 Health 工作区护栏的衔接

新增治理护栏必须服从当前工作区已存在的高优先级规则，尤其是：

- 双库切换和模拟器单实例规则
- runner / supervisor 单实例和结构化结果规则
- 验证优先、证据优先规则
- 隐私数据与真实业务写入保护
- “每轮只允许一个主问题”的自我进化节奏

因此，本护栏不能被解释为“skills / MCP 可以为了自证价值而越过现有护栏”。

## 16. 建议落地方式

第一版实现建议只做文档 + 流程护栏：

1. 在根级 `AGENTS.md` 新增 `Skills 与 MCP 自评/自进化/软淘汰护栏` 章节。
2. 将本设计中的治理对象、状态机、证据规则、自动权限、禁区、人工接管点压缩成执行口径。
3. 将对象级别的待处理问题和状态建议记入 `tests/evolution-backlog.json` 或后续治理台账。
4. 暂不在第一版引入复杂自动评分脚本。

## 17. 验收标准

第一版护栏落地后，应满足：

- `AGENTS.md` 中存在一段明确、强制、可执行的 skills / MCP 治理规则。
- 任何人阅读后都能区分 `candidate / active / restricted / soft-retired / frozen`。
- 任何升降级和软淘汰决策都必须能回溯到本地证据。
- 外部 / 内置对象不会被误当成本地可写对象自动修改。
- 自动进化不会绕过现有双库、runner、隐私、验证护栏。
- 软淘汰默认是不再自动调用，而不是物理删除。
